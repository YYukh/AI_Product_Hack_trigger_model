# Реалистичный оракул: верхняя граница выгоды

Артефакт фазы 1, гипотеза Г4. Даёт верхнюю границу шкалы, против которой измеряется сигнал — обосновывает метрику «выгода момента в bp» из раздела 7.1 кейса и снимает главный контраргумент жюри «а с чем вы вообще сравниваете».

---

## 1. Определение

**Реалистичный оракул** — выгода от идеального выбора дня перевода внутри окна гибкости клиента.

Клиент осознаёт потребность в день `t0` и готов подождать до `W` дней. Оракул знает будущее внутри `[t0, t0+W-1]` и выбирает день с минимальной ценой валюты получателя в рублях.

Это верхняя граница для **всего класса решений «подскажи день»**, а не только для нашей модели. Ни один сигнал не может дать клиенту больше.

**Не путать с абсолютным оракулом** (лучший день календарного месяца): тот отвечает на вопрос «сколько денег лежит в месяце», реалистичный — «сколько из них доступно клиенту». Именно смешение этих двух чисел — риск, отдельно предупреждённый в разделе 8 ниже.

---

## 2. Обозначения и допущения

| | |
|---|---|
| `p(t)` | цена **одной единицы** валюты получателя в рублях на дату `t`, после нормировки номинала |
| Направление | ниже `p` = лучше для клиента |
| Индекс | календарный, все дни, с ffill на выходных и праздниках |
| `is_stale(t)` | флаг: в этот день курс не публиковался, значение перенесено |
| `W` | окно гибкости клиента, **в календарных днях** |
| bp | базисный пункт, 0,01% |

**Допущения:**
1. Спред банка между соседними днями примерно постоянен → сокращается в отношении, расчёт по публичному ряду валиден для задачи выбора дня.
2. Ожидание внутри окна ничего не стоит клиенту. Упрощение: реально отсрочка имеет цену (дома ждут). Это делает оракул завышенным — фиксируем как консервативное допущение в пользу продукта, то есть настоящий потолок ниже.
3. Клиент переводит по курсу дня перевода, лаг публикации T+1 внутри оракула не моделируется (оракул не причинный по построению).

---

## 3. Формулы

Окно: `[t0, t0 + W - 1]` календарных дней.

```
p_min  = min p(t),   t ∈ окно
p_max  = max p(t),   t ∈ окно
p_mean = mean p(t),  t ∈ окно
```

**База «переводит сразу»** — реальное поведение, для продуктовой истории:
```
benefit_now = (p(t0) − p_min) / p(t0) × 10000   [bp]
```

**База «случайный день окна»** — сопоставимо с метрикой кейса (uplift над случайным днём):
```
benefit_rand = (p_mean − p_min) / p_mean × 10000   [bp]
```

**Плоское окно** — выбирать не из чего (календарный артефакт):
```
flat = (p_max − p_min) / p_mean × 10000 < 1 bp
```

**Отношение к шуму** — различим ли выигрыш:
```
noise  = median |p(t) − p(t−1)| / p(t−1) × 10000   [bp, по всей истории коридора]
ratio  = median(benefit_rand) / noise
```

Обе метрики выгоды односторонние (≥ 0) по построению. Это не сравнение стратегий с риском, а верхняя граница — так и подаём.

## 4. Референсная реализация

```python
import pandas as pd

def realistic_oracle(p: pd.Series, W: int) -> pd.DataFrame:
    """
    p : цена 1 единицы валюты получателя в рублях,
        календарный DatetimeIndex без пропусков, ffill применён.
    W : окно гибкости клиента в календарных днях.
    Возвращает по каждому t0 выгоду идеального выбора внутри [t0, t0+W-1].
    """
    rev = p[::-1]
    p_min  = rev.rolling(W, min_periods=W).min()[::-1]
    p_max  = rev.rolling(W, min_periods=W).max()[::-1]
    p_mean = rev.rolling(W, min_periods=W).mean()[::-1]

    df = pd.DataFrame({
        "p_now":  p,
        "p_min":  p_min,
        "benefit_now_bp":  (p - p_min) / p * 1e4,
        "benefit_rand_bp": (p_mean - p_min) / p_mean * 1e4,
        "flat_window":     (p_max - p_min) / p_mean * 1e4 < 1,
    })
    return df.dropna()          # последние W-1 наблюдений неполные


def oracle_summary(p: pd.Series, windows=(1, 3, 5, 7, 10, 14, 30)) -> pd.DataFrame:
    noise = (p.diff().abs() / p.shift()).median() * 1e4
    rows = []
    for W in windows:
        d = realistic_oracle(p, W)
        live = d[~d.flat_window]
        rows.append({
            "W": W,
            "median_now_bp":   d.benefit_now_bp.median(),
            "median_rand_bp":  d.benefit_rand_bp.median(),
            "p25_rand_bp":     d.benefit_rand_bp.quantile(.25),
            "p75_rand_bp":     d.benefit_rand_bp.quantile(.75),
            "p90_rand_bp":     d.benefit_rand_bp.quantile(.90),
            "flat_share":      d.flat_window.mean(),
            "median_live_bp":  live.benefit_rand_bp.median(),
            "noise_bp":        noise,
            "ratio_to_noise":  d.benefit_rand_bp.median() / noise,
        })
    return pd.DataFrame(rows)
```

**Проверки после запуска:**
- `benefit` не может быть отрицательным — если появился, перевёрнут знак или сдвинут индекс.
- `flat_share` при `W=1` должна быть равна 1,0 — санити-чек всей конструкции.
- `median_rand_bp` монотонно растёт по `W`. Если нет — ошибка в реверсивном rolling.

## 5. Прогоны и разрезы

| Прогон | Зачем |
|---|---|
| Базовый: все `t0`, вся история, 5 коридоров, 7 значений `W` | основная таблица |
| По годам | режим волатильности меняется; проверка, что вывод не держится на одном аномальном годе |
| `t0 ∈ {5-е, 20-е число}` | проверка чувствительности к дню зарплаты, которого мы не знаем. Расхождение с базовым < 15% → пробел в данных не критичен |
| С исключением плоских окон (`median_live_bp`) | сколько выгоды доступно, когда выбирать реально есть из чего |
| Абсолютный оракул (`W=30`) | справочная линия на графике |

## 7. Критерии решения

| Условие при `W=7` | Вывод |
|---|---|
| `median_rand_bp ≥ 100` и `ratio_to_noise ≥ 2` | коридор в работу |
| `median_rand_bp < 100` либо `ratio_to_noise < 2` | коридор неперспективен → в отчёт как честный отрицательный результат, модель не крутим |
| `flat_share > 0,3` при `W=3` | минимальное рабочее окно продукта — не менее 5 дней; фиксируем как продуктовое ограничение |
| прирост медианы от `W=7` к `W=14` < 20% | целевое окно продукта — неделя, требовать большей гибкости бессмысленно |

## 8. Как формулировать в презентации

Перевод в рубли обязателен: `benefit_bp / 10000 × средний чек`.

Шаблон фразы:

> «В окне одной недели идеальный выбор дня стоит **180 bp** — это **900 ₽** на переводе 50 000 ₽. Наш сигнал забирает **60 bp** из этих 180, то есть треть доступного потолка.»

Это закрывает критерий 2 рубрики Demo Day (польза для клиента в понятных показателях) и одновременно задаёт честную рамку: мы не обещаем весь размах курса, мы говорим, какую его часть реально забираем.

**Чего не делать:** подавать медиану месячного размаха (5,9% из брифа, см. `01_problem_and_context.md`) как ценность продукта. Клиенту доступна не она, и первый же вопрос жюри это вскроет.
